# CRM Cleaner — упрощённый план разработки

Версия 4 · 9 сентября 2026 года

Цель этого плана — быстрее получить первый работающий результат и первую внешнюю оплату, не потеряв основные гарантии безопасной очистки. Всё исключённое из первого MVP сохранено в разделе расширения и возвращается после проверки спроса.

## 1. Зафиксированные решения

| Вопрос | Решение |
| --- | --- |
| Цель | Получить первую внешнюю оплату и проверить коммерческий спрос |
| Первый пользователь | Иван, собственный портал Bitrix24 |
| Первый MVP | Сделки |
| Масштаб | До 3 000 записей за операцию |
| Выполнение | В браузере внутри Bitrix24, без собственного backend очистки |
| Хостинг | SprintHost; PHP только для минимальной точки входа приложения |
| Интерфейс | React + TypeScript + Vite |
| Первый браузер | Актуальный настольный Chrome; остальные после первого платежа |
| Основной сценарий | Фильтр → полный preview → исключения → CSV → подтверждение → прогресс → результат |

Первой сущностью выбраны сделки. Границу данных строим через адаптер, но ветку лидов одновременно не реализуем.

## 2. Состав первого платного MVP

Входит:

- одна выбранная сущность CRM;
- дата создания или изменения, статус/стадия и ответственный; для сделок — воронка;
- полный сбор до 3 000 записей без тихого обрезания;
- таблица preview и исключение отдельных записей;
- точные числа `Найдено`, `Выбрано`, `Исключено`;
- CSV выбранных полей **до** удаления;
- финальное подтверждение с точным количеством, без контрольной фразы;
- фиксированный набор ID, который не расширяется после подтверждения;
- пакетное удаление, прогресс и отдельный результат каждого ID;
- остановка новых запросов, понятные ошибки и ограниченный retry временных отказов;
- простой локальный checkpoint незавершённой операции и локальный lock от двойного запуска;
- удаление только для администратора текущего портала.

Не входит до первой оплаты:

- вторая CRM-сущность;
- очистка списка чатов и scope `im`;
- контакты, компании, открытые линии, задачи, Диск, дубли и AI;
- постоянная локальная история и итоговый CSV после удаления;
- автоматическое продолжение операции после закрытия вкладки;
- полноценные IndexedDB-миграции и сложная координация вкладок;
- повторная проверка контрольных полей каждой карточки перед DELETE;
- полный набор браузеров, автоматический биллинг и публикация в Marketplace.

## 3. Упрощённые правила безопасности

1. DELETE разрешён только после полного preview и отдельного подтверждения точного набора ID.
2. Пустой фильтр, нулевой результат, незавершённый сбор и выборка больше 3 000 блокируют удаление.
3. Изменение фильтра или исключений аннулирует подтверждение.
4. Preview действует ограниченное время, начальное предложение — 10 минут. После истечения его нужно собрать заново.
5. Перед отправкой сохраняется минимальный checkpoint: портал, пользователь, сущность, подтверждённые ID и их состояния. Токены не сохраняются.
6. После закрытия вкладки операция не продолжается автоматически. При возвращении показываем факт прерывания и предлагаем сначала проверить CRM, затем собрать новую выборку.
7. Потерянный ответ не считается успехом. Автоматически повторяются только явно временные ошибки, с ограничением числа попыток.
8. CSV — контрольный экспорт, а не полная резервная копия. Универсальную обратимость удаления не обещаем.

Расширенная сверка изменившихся карточек и полноценное продолжение операций возвращаются после первого платежа.

## 4. Роли

- **А — автономно:** Codex создаёт код, тесты, документацию, mock-данные и выполняет локальные проверки.
- **С — совместно:** Codex готовит конкретный результат; Иван выбирает вариант, работает с аккаунтом или разрешает внешнее действие.
- **И — Иван:** вход и 2FA, выбор реальных данных, оплаты, договорённости и подтверждение удаления.

Пароли и токены в чат не передаются. План не является разрешением удалять реальные записи или публиковать приложение.

## 5. Этапы первого MVP

### Этап 0. Один обязательный выбор

- [x] **0.1 · С:** первой сущностью выбраны сделки. Базовый сценарий — старые проигранные сделки с ограничением по дате, воронке, стадии и ответственному.
- [x] **0.2 · А:** использовать текущий репозиторий как основу проекта и сохранить существующие документы, правила и дизайн-материалы.
- [ ] **0.3 · С:** перед внешним размещением сообщить поддомен/каталог SprintHost и подтвердить тестовый портал. Эти данные не блокируют локальную разработку.

**Результат:** одна ветка продукта имеет приоритет; разработка не распараллеливается на несколько сущностей.

### Этап 1. Технический вертикальный срез

- [x] **1.1 · А:** создать React + TypeScript + Vite, строгую типизацию, lockfile, базовые lint/typecheck/test/build-команды и минимальный PHP-вход.
- [x] **1.2а · А:** выделить `BitrixAdapter`, сделать mock-адаптер и локальный экран фильтров/preview выбранной сущности без сети.
- [ ] **1.2б · А:** сделать минимальный реальный read-only адаптер выбранной сущности по отдельно утверждённому интеграционному дизайну.
- [ ] **1.3 · С:** разместить технический пакет на SprintHost, открыть его в iframe и проверить инициализацию SDK, контекст портала/пользователя и один read-only REST-вызов. Иван выполняет вход/2FA; Codex исправляет интеграцию.

**Результат:** до полировки всего интерфейса доказано, что SprintHost, PHP-вход, iframe, SDK и read-only REST-вызов работают вместе.

### Этап 2. Полезный preview

- [ ] **2.1 · А:** реализовать конфигурацию выбранной сущности, справочники и фильтры без зашитых ID стадий.
- [ ] **2.2 · А:** добавить пагинацию, дедупликацию и полный сбор; при результате больше 3 000 требовать сузить фильтр.
- [ ] **2.3 · А:** сделать таблицу, ссылки на карточки, исключение/возврат строк, точные счётчики, безопасный CSV и финальное модальное окно.
- [ ] **2.4 · С:** Иван сравнивает read-only выборку и CSV с Bitrix24 и проверяет несколько граничных карточек. Это не разрешение удаления.

**Результат:** приложение уже можно показать потенциальному покупателю как работающий анализатор, не выполняющий изменений.

### Этап 3. Выполнение удаления

- [ ] **3.1 · А:** зафиксировать подтверждённый набор ID; добавить проверку администратора, срока preview, контекста, checkpoint и простой lock от двойного запуска.
- [ ] **3.2 · А:** реализовать небольшие последовательные пакеты `crm.item.delete`, прогресс и состояния каждого ID: ожидает, отправлен, удалён, ошибка, неизвестно.
- [ ] **3.3 · А:** добавить ограниченный retry временных ошибок, ожидание REST-лимита, паузу и остановку новых запросов.
- [ ] **3.4 · А:** реализовать итог и повторное открытие: неизвестные исходы показываются отдельно, автоматического продолжения нет; выполнить 12 блокирующих mock-проверок.

**Результат:** основной опасный сценарий проходит на mock API и не расширяет подтверждённый список.

Локальная часть на 10 сентября 2026: реализованы CSV, подтверждение/срок списка,
демо-контекст администратора, последовательный mock-исполнитель, IndexedDB checkpoint,
Web Locks, пауза/остановка, retry и отчёт без автостарта. Подшаги 2.3 и 3.1–3.4
не отмечены целиком: ссылки/справочники/права настоящего портала, реальный транспорт
и все 12 блокирующих сценариев ещё не подтверждены. Подробные результаты — TEST-MATRIX.

### Этап 4. Контролируемая проверка на Bitrix24

- [ ] **4.1 · С:** Codex готовит помеченные искусственные записи и контрольные ID; Иван разрешает точный набор. Сначала проверяется одна запись.
- [ ] **4.2 · С:** разрешёнными сериями проверить 10, 50 и 51 запись, ошибку прав, временный сетевой отказ, паузу и исключённую контрольную запись. Объём 3 000 до этого проверяется на mock.
- [ ] **4.3 · С:** Иван проверяет итог и отдельно подтверждает первую реальную выборку до 3 000 записей; Codex фиксирует результаты и ограничения в `STATUS.md` и `TEST-MATRIX.md`.

**Результат:** собственная задача очистки выполнена контролируемо; это подтверждает работоспособность, но ещё не коммерческий спрос.

### Этап 5. Первая внешняя оплата

- [ ] **5.1 · С:** после рабочего preview Codex готовит короткое предложение и демонстрацию; Иван выбирает стартовую цену и 2–3 потенциальных клиента.
- [ ] **5.2 · С:** провести платную ручную установку на втором портале без автоматического биллинга. Владелец сам проверяет и подтверждает выборку.
- [ ] **5.3 · С:** Codex исправляет дефекты, проверяет изоляцию порталов и готовит релизный пакет; Иван фиксирует фактическую оплату и обратную связь.

**Результат:** подтверждена либо опровергнута готовность внешнего пользователя платить за безопасную массовую очистку.

## 6. Проверки, блокирующие первый MVP

До реального удаления обязательны 12 сценариев из `TEST-MATRIX.md`: `T01`, `T02`, `T03`, `T04`, `T05`, `T07`, `T10`, `T11`, `T13`, `T14`, `T20`, `T22`.

Дополнительно вручную проверяются:

- точное совпадение preview, CSV, подтверждения и отправленных ID;
- отсутствие DELETE для исключённой контрольной записи;
- остановка новых запросов после паузы или ошибки;
- отсутствие секретов в клиентской сборке и логах;
- понятное поведение после закрытия и повторного открытия вкладки.

Остальные сценарии матрицы сохраняются, но не блокируют первый сопровождаемый платный пилот, если не относятся к найденному дефекту.

## 7. Расширение после первой оплаты

Ничего из прежнего плана не удаляется. Возвращаем функции небольшими проверяемыми дополнениями:

1. Вторая CRM-сущность через уже созданную конфигурацию.
2. Очистка списка чатов через `im.recent.list` / `im.recent.hide`; личные и групповые диалоги, без удаления сообщений. Открытые линии — отдельная проверка.
3. Постоянная локальная история и итоговый CSV после операции.
4. IndexedDB, версии схемы и полноценное восстановление незавершённых операций.
5. Расширенная координация вкладок и сверка изменившихся карточек перед удалением.
6. Остальные браузеры и полный набор из 35 тестовых сценариев.
7. Контакты, компании и готовые пресеты очистки.
8. Автоматический биллинг, Marketplace и публичная документация.
9. CRM Hygiene: поиск тестовых, пустых, старых и подозрительных данных.

Каждое дополнение получает отдельную задачу, приёмку и решение о влиянии на цену. Расширение не должно останавливать уже работающий платный сценарий.

## 8. Следующий шаг

Следующий шаг — минимальный реальный read-only адаптер сделок по отдельному интеграционному дизайну. Локальный сценарий до демо-удаления уже реализован; SprintHost и тестовый портал понадобятся для совместной проверки этапа 1.3.
