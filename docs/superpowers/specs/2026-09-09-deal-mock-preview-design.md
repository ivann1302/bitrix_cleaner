# Deal Mock Preview — Design

Дата: 9 сентября 2026 года. Статус: утверждён для планирования.

## Цель

Создать первый локальный вертикальный срез CRM Cleaner для сделок: пользователь задаёт условия старых проигранных сделок, запускает поиск по искусственным данным и проверяет полный preview с исключениями и точными счётчиками.

Срез доказывает структуру приложения, UX фильтрации и границу данных до подключения Bitrix24. Он не выполняет сетевые запросы и не содержит пути удаления.

## Объём

Входит:

- React + TypeScript + Vite-каркас и минимальная PHP-точка входа;
- фильтры по полю даты создания или изменения, верхней границе даты, воронке, проигранной стадии и ответственному;
- типизированный `BitrixAdapter` и локальный `MockBitrixAdapter`;
- состояния initial, loading, ready, empty, over-limit и failure;
- таблица preview сделок, исключение и возврат строк;
- счётчики `Найдено`, `Выбрано`, `Исключено`;
- проверка актуальности асинхронного ответа по ревизии поиска;
- адаптивный интерфейс по действующей дизайн-системе;
- unit- и UI-тесты, lint, typecheck и production build.

Не входит:

- реальный SDK или REST API Bitrix24;
- авторизация, проверка администратора и портал пользователя;
- CSV, подтверждение и DELETE;
- checkpoint, IndexedDB, блокировка вкладок и восстановление;
- лиды и другие CRM-сущности;
- публикация на SprintHost.

## Основной сценарий

1. Приложение открывается сразу на экране условий для сделок; отдельного выбора сущности нет.
2. По умолчанию пользователь готовит поиск проигранных сделок до выбранной даты.
3. Пользователь выбирает, к какому полю относится дата: создание или изменение. Воронка, стадия и ответственный уточняют выборку.
4. По нажатию `Найти сделки` форма проходит локальную проверку и запускает новую ревизию поиска.
5. Во время ожидания интерфейс сообщает, что данные только читаются и удаление не выполняется.
6. После полного ответа пользователь видит таблицу, счётчики и условия выборки.
7. Пользователь может исключать и возвращать строки; отправки опасных команд в этом срезе не существует.

Пустой фильтр не отправляется адаптеру. Верхняя граница даты интерпретируется как конец выбранного календарного дня в явно показанном локальном часовом поясе mock-портала.

## Архитектура

Выбран вертикальный срез через адаптер, а не статичный UI и не раннее подключение живого портала.

- `app` создаёт адаптер, управляет текущим экраном и связывает форму с preview.
- `deals/domain` содержит типы сделки, критерии поиска, результат и чистые правила валидации/счётчиков.
- `deals/data` определяет `BitrixAdapter` и реализует `MockBitrixAdapter`.
- `deals/ui` содержит фильтры, состояния поиска, таблицу и сводку.
- `shared/ui` содержит только действительно повторяемые визуальные примитивы.

UI зависит от интерфейса адаптера, но не от реализации mock. Будущий read-only адаптер сможет реализовать тот же контракт без изменения доменных правил и компонентов preview.

Минимальный контракт:

```ts
type DateField = "createdAt" | "updatedAt";

interface DealSearchCriteria {
  readonly dateField: DateField;
  readonly beforeDate: string | null;
  readonly pipelineId: string | null;
  readonly stageId: string | null;
  readonly assignedById: string | null;
}

type DealSearchResult =
  | { readonly kind: "success"; readonly items: readonly Deal[] }
  | { readonly kind: "empty" }
  | { readonly kind: "over-limit"; readonly matchedAtLeast: number }
  | { readonly kind: "failure"; readonly code: DealSearchErrorCode };

interface BitrixAdapter {
  getDealFilterOptions(): Promise<DealFilterOptions>;
  searchDeals(criteria: DealSearchCriteria): Promise<DealSearchResult>;
}
```

Точные поля `Deal` ограничиваются preview: ID, название, воронка, стадия, ответственный, дата создания и изменения. Mock IDs — строки, как и нормализованные будущие ID API. Для `over-limit` действует инвариант `matchedAtLeast > 3000`; успешный результат нормализуется до уникальных сделок по ID.

## Поток состояния

Состояние поиска — дискриминированное объединение, а не набор независимых флагов:

- `initial` — форма доступна, результата нет;
- `loading` — хранит ревизию и нормализованные критерии;
- `ready` — хранит ревизию, критерии, неизменяемый список и множество исключённых ID;
- `empty`, `over-limit`, `failure` — хранят ревизию и критерии соответствующего запуска.

Каждая отправка формы увеличивает ревизию. Результат применяется только при совпадении ревизии с текущей; поздний ответ старого поиска игнорируется. Изменение фильтра не меняет уже показанный результат, пока пользователь не запустит новый поиск, но интерфейс помечает preview как не соответствующий введённым условиям и не предлагает продолжение опасного сценария.

`Найдено` равно длине полного списка, `Исключено` — размеру множества исключённых ID, `Выбрано` — разности этих значений. Эти числа вычисляются из одного состояния и не хранятся отдельными изменяемыми копиями.

## Mock-данные

Обычный mock-набор содержит детерминированные сделки в нескольких воронках, с разными датами, ответственными и стадиями. Названия и пользователи вымышлены. Адаптер действительно применяет критерии к набору, а не возвращает один заранее подготовленный экран.

Для тестов адаптер создаётся с переданным набором и управляемым поведением. Это позволяет без тысяч объектов проверить empty, 3 000/3 001, failure, задержку и порядок ответов. В production mock-сборке нет скрытого переключения на реальную сеть.

## Интерфейс

Композиция следует `docs/DESIGN-SYSTEM.md` и макетам фильтров/preview:

- светлый фон, белые поверхности и бирюзовый основной акцент;
- шапка с названием и явной меткой `Демо-режим`;
- форма условий слева и сводка выбранных условий справа;
- после поиска — таблица и панель `К проверке` со счётчиками;
- таблица показывает полный набор через клиентскую пагинацию по 25 строк, а исключения и счётчики относятся ко всему результату, не только к текущей странице;
- `Найти сделки` — бирюзовая кнопка;
- `Исключить` и `Вернуть` — текстовые нейтральные действия;
- красных кнопок нет, потому что этот срез ничего не удаляет.

Поля имеют видимые labels. Состояния и ошибки сообщаются текстом, а не только цветом. Таблица доступна с клавиатуры, строки имеют стабильный ключ ID, загрузка объявляется через умеренный live-region. На узкой ширине сводка располагается над таблицей, горизонтальная прокрутка ограничена областью таблицы.

## Ошибки и границы

- Хотя бы одно содержательное ограничение обязательно; один выбор `dateField` ограничением не считается.
- Невалидная календарная дата блокирует поиск и связывается с полем.
- `empty` не смешивается с `failure`.
- `over-limit` не содержит частичного списка и предлагает сузить фильтр.
- Неизвестный код ошибки отображается безопасным общим текстом без технических данных.
- Названия сделок выводятся как текст; `dangerouslySetInnerHTML` не используется.
- Ни компонент, ни Effect не содержит DELETE или автоматического запуска поиска.

## Проверки

Доменные тесты:

- пустой и валидный фильтры;
- фильтрация по созданию и изменению;
- сочетание воронки, стадии и ответственного;
- границы 0, 1, 3 000 и 3 001;
- дедупликация ID в mock-результате;
- исключение/возврат и точные счётчики;
- игнорирование позднего ответа старой ревизии.

UI-тесты:

- доступные labels и клавиатурные действия;
- переход initial → loading → ready;
- empty, over-limit и failure имеют разные сообщения;
- изменение фильтра помечает текущий preview устаревшим;
- исключённый ID отсутствует в выбранном наборе;
- интерфейс не содержит действия удаления.

Критерий готовности: проходят `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` и PHP lint; локальный preview визуально сверяется с дизайн-системой. Живой Bitrix24 и SprintHost этим результатом не проверяются.

## Следующий шаг после среза

После приёмки локального mock-preview отдельно проектируется минимальный read-only адаптер сделок и проверка iframe на согласованном тестовом портале. Подключение реальных данных не добавляет DELETE и не считается разрешением очистки.
