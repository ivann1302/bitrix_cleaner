# Подготовка read-only пилота

Подготовлены локальные кандидаты для этапа 1.3, а не завершённая установка в Bitrix24. С 12 сентября 2026 года повторная сборка автоматизирована: `npm run package:release` (описание ниже).

## Предыдущий пакет — 11 сентября

Локальный архив: `.superpowers/releases/crm-cleaner-81f801d.zip`.

SHA-256: `ba7acdd4710b2339bbc3cfd90987026c2e910e8232be9ac0c76db8703d43bfac`.

В корне архива находятся `index.html`, `index.php` и `assets/` с одним JS и одним CSS. Документы, `.git`, `.agents`, `.env`, исходники и `node_modules` в него не включены. Архив находится в игнорируемом каталоге и не хранится в Git.

JS содержит и real read-only режим, и искусственные данные demo. Прямое открытие страницы запускает demo; в iframe приложение инициализирует SDK. Поэтому успешное прямое открытие ещё не доказывает установку в Bitrix24.

## Что проверено для предыдущего пакета

- После fast-forward объединения в `main`: 290 тестов в 25 файлах, сборка, ESLint и Prettier прошли.
- PHP 8.5.4 через локальный сервер: GET и POST `/dist/index.php` вернули HTTP 200, `text/html; charset=UTF-8` и содержимое, побайтно равное собранному `index.html`. POST содержал только искусственный параметр `probe=local-test`.
- Относительные JS/CSS URL из HTML разрешились внутри `/dist/assets/`, оба вернули HTTP 200 и побайтно совпали с файлами сборки.
- `unzip -t` подтвердил целостность архива. Временный локальный сервер остановлен после проверки.

Это проверки PHP/HTTP и путей. HTTPS, заголовки хостинга, настоящий iframe, SDK postMessage, scopes и права портала пока не проверены.

## Перед размещением

Нужно получить от владельца адрес HTTPS, точный каталог SprintHost и адрес тестового портала, а также разрешение на загрузку этой версии и установку/изменение приложения в указанном портале. Пароли, токены и тела авторизационных POST в переписку не передаются; вход и 2FA выполняет владелец.

Для первого пилота предпочтителен отдельный пустой каталог. Если по адресу уже работает приложение, сначала сохранить его текущие файлы и уточнить разрешённую замену. Подготовка этого архива не разрешает перезаписывать существующий сайт.

## Порядок внешней проверки

1. Проверить хеш архива и распаковать его содержимое в согласованный каталог. Не загружать весь репозиторий.
2. Открыть точный URL `index.php` по HTTPS. Проверить HTTP-ответ, отсутствие ошибок загрузки JS/CSS и правильные относительные пути. Проверить PHP-версию и настройки логирования в панели хостинга: тела служебных POST и авторизационные параметры не должны записываться.
3. На тестовом портале выбрать поддерживаемый способ установки и сверить его актуальные требования с официальной документацией Bitrix24. URL открытия указывает на согласованный PHP-вход. Список scopes и необходимость отдельного install-handler проверяются для конкретного типа установки; текущий PHP только отдаёт HTML и не подтверждён как обработчик установки.
4. Открыть приложение из портала. Ожидается отметка «Bitrix24 · только чтение», правильные портал, пользователь и признак администратора. Ошибка инициализации должна показать ошибку, а не demo.
5. Собрать маленькую выборку сделок по известным условиям. Сверить несколько ID, стадию, воронку, ответственного и границы даты с CRM. Проверить ссылки и CSV.
6. Переключиться на лиды: прежняя выборка исчезает, воронки нет, доступны только неуспешные статусы. Повторить сверку небольшого preview и CSV. Проверить отсутствие кнопки подтверждения удаления для обоих типов.
7. Записать результат и ограничения в `docs/TEST-MATRIX.md` и `docs/STATUS.md`. Этап 1.3 отмечать выполненным только после фактического успешного открытия SDK и read-only REST-вызова; этап 2.4 — после сверки выборок владельцем.

При неверном контексте или составе выборки прекратить испытание. Пакет не содержит реального транспорта удаления. Испытания DELETE относятся к отдельному этапу с точными искусственными ID и отдельным разрешением.

## Повторная сборка

В checkout согласованной версии выполнить `npm run package:release`. Нужны установленные зависимости из lockfile, поддерживаемый Node/npm и локальные `git`, `zip`, `unzip`. Команда последовательно выполняет тесты упаковки, TypeScript, ESLint, Prettier, тесты приложения и новую production-сборку. При ошибке проверок упаковка не запускается. Сетевых запросов и размещения команда не выполняет.

Результат создаётся в новом уникальном каталоге `.superpowers/releases/crm-cleaner-<revision>-<suffix>/`:

- `crm-cleaner.zip`: только `index.html`, `index.php`, хешированные JS/CSS из `assets/`, на которые ссылается HTML, и `THIRD-PARTY-NOTICES.txt` с лицензиями библиотек, фактически включённых Vite в сборку.
- `SHA256SUMS`: SHA-256 архива; проверить из этого каталога командой `sha256sum -c SHA256SUMS`.
- `manifest.json`: время упаковки, полный Git revision, явный `git.dirty`, размер и SHA-256 каждого публичного файла и хеш архива. Манифест и контрольная сумма не входят в публичный архив.

Упаковщик отказывается принимать отсутствующие или пустые обязательные файлы, лишние файлы, source maps, символические ссылки и некорректные/внешние пути assets. Разрешён текущий формат сборки с JS/CSS, непосредственно указанными в HTML; при добавлении динамических чанков или других ресурсов нужно отдельно обновить allowlist и тесты. Скрипт проверяет структуру пакета и целостность ZIP, но не заменяет браузерную проверку или аудит содержимого JS/PHP. Существующие архивы не перезаписываются; неуспешный запуск может оставить неполный уникальный каталог без полного комплекта метаданных.

Незакоммиченные изменения разрешены для локального кандидата и отмечаются `git.dirty: true`; такой пакет нельзя выдавать за точное содержимое указанного commit. Перед согласованным размещением использовать проверенный commit без локальных изменений, сверить манифест и записать новый путь/хеш. Пересборка может изменить архив, поэтому старый хеш нельзя переносить без проверки. Тесты упаковки отдельно: `npm run test:release` (Node test runner, искусственные каталоги в системном tmp, без CRM).
