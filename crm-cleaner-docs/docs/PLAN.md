# CRM Cleaner — новый план разработки

Версия 2 · 9 сентября 2026 года

Этот план заменяет предыдущий вариант с PHP-backend, Laravel, серверной БД и cron. Здесь очистка выполняется в браузере. Документ описывает будущую работу; приложение ещё не разработано и не опубликовано.

## 1. Что уже решили

| Вопрос | Решение |
| --- | --- |
| Цель | Получить первые оплаты и проверить коммерческий спрос |
| Первый пользователь | Иван, собственный портал Bitrix24 |
| Первый сценарий | Удаление накопившихся старых лидов или сделок |
| Масштаб | До 3 000 записей за одну операцию |
| Хостинг | Существующий SprintHost; тариф и поддомен ещё нужно указать |
| Выполнение | В браузере пользователя, без собственного backend обработки CRM |
| PHP | Только минимальная страница открытия/установки приложения, если нужна для работы iframe и хостинга |
| UX | Тип → фильтры → список и исключения → подтверждение → прогресс → отчёт |

«Без сервера» означает отсутствие собственного backend для запросов CRM, токенов и заданий. Файлы интерфейса размещаются на SprintHost, а сами CRM-запросы обрабатывает Bitrix24.

## 2. Рабочие предложения, которые не выдаём за согласованные решения

- **Первый коммерческий MVP — лиды и сделки.** Предлагаю отложить контакты, компании, диалоги, Диск, дубли и AI, чтобы быстрее проверить оплату за основной сценарий.
- **Порядок реализации — сначала сделки, затем лиды.** Если первая реальная задача окажется в лидах, меняем порядок до подключения данных, не архитектуру.
- **Базовый отбор — по дате создания или изменения, стадии/статусу, ответственному; для сделок также по воронке.** Дату и статусы первой очистки Иван выбирает перед приёмкой фильтров. «Давно не общались» не приравниваем к «давно не изменяли»: анализ звонков/писем не включён по умолчанию.
- **Технологии интерфейса — React + TypeScript + Vite; локальное хранение — IndexedDB.** Dexie можно использовать как библиотеку доступа к IndexedDB. Версии фиксируются при создании проекта.
- **Внешний вид принят: мягкий бирюзовый минимализм.** Светлый мастер с хорошо заметными числами и таблицей; красный используется только по семантике удаления. Токены, компоненты и состояния зафиксированы в `docs/DESIGN-SYSTEM.md`; детализация экрана проверяется на прототипе этапа 1.

Эти вопросы не блокируют создание локального каркаса на искусственных данных. Они должны быть закрыты до соответствующего теста, удаления или коммерческого предложения. Цену и модель оплаты пока не выбрали.

## 3. Как устроена браузерная версия

| Где | Что выполняется |
| --- | --- |
| SprintHost | Выдаёт PHP-страницу и собранные HTML/JS/CSS; не выполняет очистку и не хранит задания |
| Браузер внутри Bitrix24 | Показывает интерфейс, собирает выборку, отправляет REST-запросы через библиотеку Bitrix24, обрабатывает результаты |
| IndexedDB этого браузера | Хранит список ID, исключения, состояние операции и локальную историю |
| Bitrix24 | Проверяет действительные REST-права пользователя и выполняет запросы к CRM |

Node.js нужен локально для сборки интерфейса. Постоянный Node-процесс, Laravel, MySQL, Redis, cron, VPS и собственный сервер оплаты в этот план не входят.

Библиотека [BX24.init](https://apidocs.bitrix24.ru/sdk/bx24-js-sdk/system-functions/bx24-init.html) получает контекст приложения от родительского iframe. Реальный способ установки, авторизации и работы SDK проверяем на SprintHost на этапе 2. Если для выбранного способа распространения необходим backend, не добавляем его молча: отдельно выбираем допустимый путь в рамках требования пользователя.

### Ограничения, которые влияют на продукт

1. Закрытие вкладки прекращает отправку новых запросов. Уже отправленные запросы могут завершиться. Фоновая вкладка и сон компьютера также могут задерживать работу; скорость не гарантируется.
2. Продолжение возможно, если сохранились локальные данные и доступен нужный портал/пользователь. Старое незавершённое состояние не запускается автоматически: сначала сверка результатов и явное действие пользователя.
3. История привязана к браузерному контексту и устройству. Это не централизованный аудит; браузер может удалить данные или запретить хранилище. Основание — [правила квот и удаления браузерного хранилища](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
4. Проверка «только администратор» в UI — ограничение штатного сценария приложения. Она не заменяет серверную проверку прав Bitrix24 и не защищает от изменённого клиентского кода. REST-удаление подчиняется [правам crm.item.delete](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-delete.html).
5. PHP-страница может получать служебный контекст установки/входа. Не сохраняем и не выводим тела таких запросов или токены. Секрет приложения и refresh token не размещаем в JS, IndexedDB, исходниках или отчётах; текущую авторизацию используем штатным механизмом SDK.
6. Если локальное хранилище недоступно или запись в него перестала работать, новые удаления не отправляются. Уже отправленные результаты могут остаться неопределёнными.

## 4. Что входит в первый релиз

- Лиды и сделки; одна сущность на операцию — предложение по сокращению MVP.
- Фильтры, предварительный подсчёт и сбор полного списка до 3 000 записей.
- Таблица с ID, названием, статусом/стадией, ответственным и датами; ссылка на карточку CRM.
- Исключение нужных записей из удаления и точные числа «найдено / выбрано / исключено».
- CSV перед очисткой, отдельное подтверждение с точным количеством и пакетное удаление.
- Прогресс, пауза, отмена остатка, ошибки и проверяемое продолжение.
- Локальная история и итоговый CSV.

Если подходящих записей больше 3 000, просим сузить фильтр. Не выбираем молча первые 3 000. CSV — экспорт выбранных полей, а не полная резервная копия CRM.

## 5. Кто что делает

- **А — автономно:** Codex пишет код, макеты, тесты и документацию; выполняет локальные проверки на искусственных данных.
- **С — совместно:** Codex готовит конкретный результат или действие, Иван принимает решение, предоставляет контекст либо разрешает оговорённое действие с аккаунтами/данными.
- **И — Иван:** вход и 2FA, оплаты и договоры, согласие владельца портала, окончательное разрешение публикации.

Повторно согласовывать каждую локальную правку не нужно. Одна разрешённая серия испытаний может выполняться автономно в согласованных пределах. Она не даёт права удалять другие данные, менять тариф или публиковать приложение. Пароли и токены в чат не передаются.

### Этап 5. Реализовать удаление и продолжение на имитации API

- [ ] **5.1 · А:** реализовать состояния операции и каждого ID. Отдельно учитывать ожидающие, отправленные, подтверждённо удалённые, ошибки, пропущенные изменения и неизвестные результаты; сохранять состояние перед отправкой и после ответа.
- [ ] **5.2 · А:** начать с одной команды, затем добавить небольшие последовательные пакеты. Размер и темп выбирать по актуальным ограничениям API. Перед удалением повторно проверять доступные контрольные поля; обнаруженные изменения пропускать. Если проверка недоступна, не считать её успешной.
- [ ] **5.3 · А:** добавить ограниченные повторы временных отказов, ожидание REST-лимитов, паузу, отмену остатка и обработку истёкшей авторизации. Успешный HTTP-ответ пакета не означает успех каждой команды; права и неверные параметры бесконечно не повторять.
- [ ] **5.4 · А:** после обрыва связи или повторного открытия сверять незавершённые записи. Потерянный ответ означает неизвестный результат. Отсутствующая/недоступная карточка не доказывает, что её удалил Cleaner. Продолжение — только явное, без слепого повтора всего пакета и без добавления новых ID.
- [ ] **5.5 · А:** добавить прогресс, локальную историю и итоговый CSV; выполнить обязательные тесты из раздела 7, включая прерывание после отправки и отказ IndexedDB. Не полагаться на обработчик закрытия страницы как на гарантированную запись последнего состояния.

**Результат:** безопасное поведение подтверждено на mock API. Список не расширяется, результаты не теряются молча, неизвестные исходы не показываются как успешные. Реальные DELETE ещё не выполнялись.

**Результат:** первая реальная задача выполнена контролируемо, а приложение прошло тесты на обеих заявленных сущностях. Объём «до 3 000» подтверждается испытаниями; заранее не обещаем число минут.

### Этап 7. Проверить оплату и подготовить распространение

- [ ] **7.1 · А:** проверить перед релизом изоляцию порталов/пользователей, XSS через поля CRM, безопасные ссылки/CSV, отсутствие секретов в сборке и логах, корректное обновление локальной схемы без автостарта старых операций.
- [ ] **7.2 · А:** подготовить релизный пакет, инструкцию установки/отката файлов, справку, реальные скриншоты и краткое коммерческое предложение. Описать закрытие вкладки, локальную историю, лимит 3 000 и отсутствие гарантии восстановления через CSV/корзину.
- [ ] **7.3 · С:** выбрать цену и допустимую модель оплаты после проверки правил распространения. Составить список 2–3 внешних потенциальных пользователей; Иван связывается с ними либо отдельно разрешает конкретные сообщения. Собственный портал проверяет удобство, а внешние оплаты — коммерческий спрос.
- [ ] **7.4 · С:** провести платный пилот по выбранной допустимой схеме: сначала показать возможности, затем согласовать условия, установку и работу с данными. Каждый владелец подтверждает собственную выборку. Не строить надёжность ограничения оплаты на скрытой кнопке в JS.

**Результат:** есть проверенная установка для другого пользователя и возможность получить оплату по выбранной модели. Коммерческий критерий первого цикла — первая фактическая оплата и обратная связь по выполненной очистке; срок модерации и доход не гарантируются. Правила проверяем через [страницу разработчика Bitrix24](https://www.bitrix24.ru/apps/dev.php).

## 7. Обязательные проверки

| Сценарий | Ожидаемое поведение |
| --- | --- |
| 0 / 1 / 50 / 51 / 3 000 / 3 001 подходящих записей | Правильный сбор и границы; больше лимита — предложение сузить фильтр |
| Пустой фильтр или незавершённый сбор | Удаление недоступно |
| Изменили фильтр или исключили строку после подтверждения | Старое подтверждение недействительно |
| После просмотра появилась новая подходящая запись | В подтверждённый список не добавляется |
| Исключили нужную карточку | DELETE для её ID не отправляется |
| Двойной старт или вторая вкладка | Та же операция не запускается параллельно в пределах поддерживаемого браузерного контекста |
| Карточка изменилась после preview | Обнаруженное изменение пропускается; гонка между проверкой и удалением не скрывается |
| Частичный успех пакета | Результат учитывается отдельно по каждому ID |
| Ответ потерян после отправки | Неизвестный исход и сверка; без слепого повторного удаления |
| Карточка отсутствует или недоступна | Не считается автоматически удалённой приложением |
| Нет сети, истёк доступ, REST-лимит | Понятная пауза/ошибка; ограниченные повторы только где допустимы |
| IndexedDB недоступна или переполнена | Новые удаления не отправляются |
| Закрыли и вновь открыли вкладку | Нет автостарта; сверка и явное продолжение сохранившейся операции |
| Очистили данные браузера или сменили устройство | Нет обещания восстановить утраченную локальную историю |
| Нажали отмену | Новые запросы прекращаются; отправленные могут завершиться |
| Открыли другой портал/пользователя | Чужая операция не подхватывается и не показывается как своя |
| Обновили приложение | Миграция данных проверена; старые удаления не запускаются автоматически |
| В полях HTML, формула, кавычки или переносы | Безопасный вывод и экспорт |

Каждая проверка фиксируется в `docs/TEST-MATRIX.md`: ID, среда, результат, дата. Mock и реальные испытания отмечаются отдельно. Дополнительные тесты нужны для конкретного риска, а не ради количества.

## 8. Границы обещания «безопасная очистка»

- Приложение отправляет DELETE только для подтверждённых ID. Счётчик отражает именно этот список.
- Фиксируется список ID, а не неизменное состояние CRM. Повторная проверка уменьшает риск, но не делает чтение и удаление атомарными.
- Отмена не откатывает уже выполненные удаления и не гарантирует отзыв отправленных запросов.
- CSV не восстанавливает всю карточку, связи и историю. Наличие и возможности корзины проверяются в конкретном Bitrix24.
- Внутренние последствия удаления для связанных данных нужно испытать; отсутствие дополнительных DELETE в нашем коде не доказывает отсутствие таких последствий.
- Блокировка одной операции в браузере не означает глобальную блокировку между всеми устройствами и администраторами портала.
- Храним минимум данных; срок хранения локальной истории и кнопку её очистки согласуем до релиза. Не обещаем неизменяемый аудит или гарантированное хранение браузером.

## 9. Как давать задачи Codex

Работаем по одному проверяемому результату за раз. Обычная задача — 1–3 связанных подшага. В конце Codex показывает: что сделано, что проверено, что осталось и где требуется участие Ивана; обновляет `docs/STATUS.md`.

После выбора проекта этот файл нужно положить в `docs/PLAN.md`. Пример первой задачи:

> Прочитай правила репозитория и docs/PLAN.md. Выполни подшаги 1.1–1.2: React + TypeScript + Vite, минимальная PHP-страница для будущего открытия в Bitrix24 и MockBitrixAdapter. Сначала проверь среду и существующие пользовательские изменения. Приложение браузерное: не добавляй Laravel, серверную БД, cron, VPS, backend запросов CRM или биллинг. Реальный Bitrix24 и внешние изменения не разрешены. Подготовь локальный запуск и сборку, выполни доступные проверки и обнови docs/STATUS.md. Укажи, что не удалось проверить, без имитации успешного результата.

Нельзя трактовать этот план как разрешение менять аккаунты или удалять CRM. Перед тестовой серией отдельно фиксируются портал, синтетические ID, лимит и допустимые действия; после этого повторять согласованную серию можно без вопроса на каждую запись.
