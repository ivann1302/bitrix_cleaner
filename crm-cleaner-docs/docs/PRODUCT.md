# Продукт — CRM Cleaner

## Цель и первый пользователь

Цель первого цикла — получить первые оплаты и проверить коммерческий спрос. Первый пользователь — Иван, собственный портал Bitrix24. Первый сценарий — очистка накопившихся старых лидов или сделок, до 3 000 записей за одну операцию.

Проверка на своём портале показывает удобство и работоспособность. Коммерческий результат оцениваем по внешнему платному пилоту, выполненной задаче и обратной связи.

## Статус состава MVP

Предлагаем начать с лидов и сделок, сначала отработав одну сущность целиком. Сокращение первоначального состава из четырёх сущностей ещё требует приёмки пользователя. До неё не расширяем разработку на контакты, компании, диалоги, задачи, Диск, смарт-процессы, дубли и AI.

## Сценарий

1. Открыть приложение в Bitrix24 и увидеть текущий портал.
2. Выбрать тип: лиды или сделки.
3. Настроить условия и собрать выборку.
4. Дождаться полного списка; увидеть найдено, выбрано и исключено.
5. Просмотреть карточки, исключить нужные записи, при желании экспортировать CSV.
6. Сверить портал, тип, условия и количество; подтвердить конкретный список.
7. Следить за выполнением; при необходимости поставить паузу или отменить остаток.
8. Получить отчёт с отдельными успехами, пропусками, ошибками и неизвестными результатами.

## Функциональные требования

| ID | Требование и критерий приёмки |
| --- | --- |
| P01 | Одна сущность на операцию; контекст портала и пользователя определён до запросов |
| P02 | Фильтры ID, создания/изменения, ответственного, статуса/стадии; воронка только для сделок. Неприменимые поля не показываются |
| P03 | Даты имеют понятные границы и часовой пояс; дата изменения не называется датой последнего общения |
| P04 | Пустой фильтр, нулевой результат и незавершённый сбор не допускаются к удалению |
| P05 | Список содержит максимум 3 000 ID. При большем числе требуется сузить фильтр; тихого обрезания нет |
| P06 | Таблица показывает ID, название, статус/стадию, ответственного и даты, позволяет открыть карточку |
| P07 | Выбор страницы и всего списка различимы. Поиск в таблице не меняет выбранные ID |
| P08 | Исключение строки влияет на итоговый список и счётчик; в строке нет удаления в обход подтверждения |
| P09 | Подтверждение относится к порталу, типу, ревизии и точному набору ID. Отдельное модальное окно повторяет условия и точное количество; красная кнопка непосредственно запускает удаление |
| P10 | Выполнение небольшими пакетами, с состоянием каждого ID; результат пакета не подменяет результаты команд |
| P11 | Пауза/отмена останавливает новые отправки, без обещания отозвать уже отправленные |
| P12 | После прерывания выполняется сверка, продолжение только по явному действию пользователя |
| P13 | CSV до/после очистки содержит согласованные поля и корректно обрабатывает формулы, кавычки и кириллицу |
| P14 | Локальная история изолирована по порталу и пользователю; отсутствие хранилища блокирует новые удаления |
| P15 | Ошибка прав не отображается как пустая CRM; потерянный ответ не отображается как доказанный успех |

## UX

Принято направление «мягкий минимализм»: тёплый светлый фон, белые поверхности, приглушённый бирюзовый акцент, заметный счётчик и плотная читаемая таблица. Красный используется по семантике только там, где нажатие непосредственно удаляет данные; переход к подтверждению остаётся бирюзовым. Точные токены, компоненты, тексты и состояния — в [DESIGN-SYSTEM.md](DESIGN-SYSTEM.md).

Нужны состояния загрузки, нуля, ошибки, превышения лимита, ожидания API, паузы, истёкшей сессии, неизвестного результата и завершения с проблемами.

## Ограничения

Очистка работает в браузере. Закрытие вкладки прекращает новые запросы; уже отправленные могут завершиться. Сон компьютера и работа вкладки в фоне могут задерживать запросы.

Список ID фиксируется, но CRM может меняться между проверкой и удалением. Найденные изменения пропускаем; гарантии атомарности нет. Поведение связанных данных нужно проверить до поддержки соответствующих сценариев.

Локальная история может исчезнуть при очистке/вытеснении данных браузера. CSV не восстанавливает целиком карточки, связи и историю. Обратимость через корзину универсально не обещаем.

## Ещё нужно решить

- Лиды или сделки для первого реального сценария.
- Дата, статусы и остальные условия первой очистки.
- Окончательный состав коммерческого MVP и браузеры.
- Политика связанных/изменённых записей, актуальность подтверждения, срок хранения.
- Цена, модель оплаты и допустимый способ распространения без backend.

Эти вопросы не мешают локальному прототипу. До соответствующей приёмки или внешнего действия решение должно быть записано в DECISIONS.md.

## Приёмка релиза

Функции P01–P15 реализованы и проверены; обязательные сценарии TEST-MATRIX имеют результаты в нужной среде. Работа в реальном iframe и выбранных браузерах подтверждена. Иван принял UX, разрешённые тестовые серии завершены, известные ограничения опубликованы.

Условия платного пилота выбраны отдельно; план не обещает дату модерации или доход.
