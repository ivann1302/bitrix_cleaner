# Требования к коду CRM Cleaner

Применяются к выбранному проектному стеку: React, TypeScript, Vite, минимальный PHP, библиотека Bitrix24 и IndexedDB. Это требования для реализации; зависимости, конфиги и команды приложения ещё не созданы.

## 1. Общий подход

- Решать текущую задачу минимальным понятным кодом. Не добавлять универсальные фабрики, плагины, DI-контейнер или дополнительный state manager без конкретной необходимости.
- Разделить представление, доменные правила, адаптер Bitrix24 и локальное хранение. UI не формирует произвольные DELETE напрямую.
- Функции отбора, подсчёта и переходов состояния делать чистыми, насколько позволяет задача. Побочные эффекты держать на явных границах.
- Применять существующий стиль проекта. Не смешивать полезную правку с массовым форматированием соседних файлов.
- Называть сущности по смыслу: confirmedSelection, snapshotRevision, operationId. Комментарии объясняют причину ограничения, особенно перед опасным действием.
- Удалять собственные неиспользуемые импорты и код. Не чистить чужие участки «заодно».
- Одно место для каждого правила: предел 3 000 и правила допустимых переходов не дублируются между UI и исполнителем.

## 2. TypeScript

Требуем `strict: true`. Для нового кода включить также `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`, проверив совместимость при создании каркаса. Эти два флага не следует считать автоматически включёнными через strict. Основание: [strict](https://www.typescriptlang.org/tsconfig/strict.html), [индексный доступ](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html), [optional-поля](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html).

- Ответы API, записи старых версий хранилища и входящие сообщения на границе принимать как `unknown`, затем проверять структуру. TypeScript не валидирует JSON во время выполнения.
- Не лечить ошибки через `any`, двойные приведения `as unknown as T`, `@ts-ignore` или необоснованный `!`. Узкое исключение требует причины и локальной границы.
- Использовать объединения с признаком состояния для результатов и операций; различать успех, ошибку и неизвестный исход. Не заменять их независимыми флагами, допускающими невозможные сочетания.
- Нормализовать ID на границе API и одинаково представлять их дальше. Ключ включает портал, тип и ID; одинаковые числа из разных типов не объединять.
- Обработку переходов делать исчерпывающей. Добавление нового состояния должно обнаруживать необработанные ветки при проверке типов или тесте.
- Обрабатывать все Promise: await, возвращённое значение или явно обработанный отказ. Не запускать опасную операцию «в фоне» без владельца состояния.
- Разделять типы API и доменную модель только там, где нужна нормализация; не создавать копии моделей без причины.

## 3. React

- Компоненты и render остаются чистыми: никаких удалений, записи токенов или запуска исполнителя при рендере.
- Запуск удаления — явная команда после подтверждения, а не Effect, реагирующий на `confirmed=true`. Сам исполнитель находится вне жизненного цикла UI и проверяет ревизию/контекст самостоятельно.
- Вычисляемые числа и отфильтрованные строки выводить из исходного состояния; не синхронизировать несколько копий через Effects. Effects использовать для связи с внешними системами и освобождать подписки/таймеры. Основание — [React: когда Effect не нужен](https://react.dev/learn/you-might-not-need-an-effect).
- В разработке использовать StrictMode. Повторный render и повторная установка Effect не должны приводить к повторной отправке команды. [Поведение StrictMode](https://react.dev/reference/react/StrictMode).
- Асинхронный результат поиска принимать только для актуального портала и ревизии. Поздний ответ старого запроса игнорировать; отмена ожидания не означает отмену уже отправленного DELETE.
- Ключи строк — стабильные идентификаторы, не индекс отображения. Переупорядочивание таблицы не меняет выбор.
- Пропсы/состояние не мутировать. Для сложной операции предпочтительны явные переходы через reducer или отдельную модель, а не каскад setState.
- Не добавлять memo/useMemo/useCallback повсюду: применять при измеренной проблеме или требовании стабильного интерфейса. Таблицу показывать страницами; виртуализацию добавлять по измерениям.
- Не использовать `dangerouslySetInnerHTML` для данных CRM. Тексты ошибок и названия выводятся как текст.

## 4. HTML, CSS и доступность

- Использовать семантические button, label, input, table и заголовки. Интерактивный div не заменяет кнопку.
- У фильтров есть подписи; ошибки связаны с полем. Клавиатура позволяет выбрать строки, перейти к подтверждению, отменить и вернуться к таблице.
- В модальном подтверждении управлять фокусом и возвращать его после закрытия. Нельзя неожиданно отправить удаление нажатием Enter в обычном фильтре.
- Прогресс имеет доступное текстовое описание; объявления обновляются умеренно, не на каждый миллисекундный шаг. Успех/ошибка различаются текстом, не только цветом.
- Поддерживать адаптацию к размеру iframe, видимый фокус, читаемые строки и предсказуемую горизонтальную прокрутку таблицы. Не скрывать важные действия за обрезанным контентом.
- Повторяемые цвета, интервалы и размеры оформить CSS-переменными; не строить отдельную дизайн-систему без необходимости.

## 5. Vite, зависимости и сборка

- Один менеджер пакетов и один актуальный lockfile. Версии выбирать совместимые и поддерживаемые; не фиксировать «последнюю» версию по памяти.
- Vite транспилирует TypeScript, но не заменяет отдельную проверку типов. Перед релизом нужны проверка TypeScript и сборка. [Документация Vite](https://vite.dev/guide/features#typescript).
- Всё включённое в клиентскую сборку доступно пользователю. `VITE_*` нельзя использовать для client_secret, refresh token и иных секретов. [Переменные Vite](https://vite.dev/guide/env-and-mode).
- Настроить base/пути assets для фактического домена или подкаталога. Проверять готовый пакет с PHP-входом, а не только dev-сервер.
- Подключать внешнюю библиотеку SDK из официального источника по проверенному контракту; остальные зависимости фиксировать lockfile. Не добавлять скрипты аналитики и сторонние CDN без продуктовой причины.
- В публичный пакет включать только необходимые файлы приложения. `.agents`, документы разработки, тестовые данные, приватные конфиги и отладочные материалы на сайт не выкладывать.
- При обновлении зависимостей читать относящиеся к изменению breaking changes и повторять проверки затронутого сценария. Автоматическое принудительное обновление всех пакетов недопустимо.

## 6. PHP на SprintHost

PHP остаётся тонкой страницей открытия/установки. Ни CRUD-прокси к CRM, ни очередь, ни OAuth-хранилище на сервере самовольно не появляются.

- Версия PHP должна быть поддерживаемой и доступной на тарифе; сверять [сроки поддержки PHP](https://www.php.net/supported-versions.php). Проверить CLI и веб-версию отдельно, если CLI используется для проверки.
- В PHP-файлах с логикой использовать `declare(strict_types=1)`, типизированные функции и раннюю валидацию входа. Не добавлять сложные абстракции для нескольких строк обработки.
- Форматировать код по применимой [PER Coding Style](https://www.php-fig.org/per/coding-style/) PHP-FIG, с четырьмя пробелами. Версию стандарта/инструмента зафиксировать при настройке, не вводить весь Composer-стек ради статической страницы.
- Не вставлять сырой POST в HTML/JS. Для HTML применять контекстное экранирование; [htmlspecialchars](https://www.php.net/manual/en/function.htmlspecialchars.php) не заменяет безопасное кодирование JSON или проверку URL.
- Не выполнять eval, динамический include из пользовательского параметра или shell-команды из запроса. Разрешённые методы и пути обработки должны быть явными.
- Заголовки отправлять до тела ответа; согласовать iframe CSP и HTTPS с Bitrix24. Не запрещать встраивание универсальным заголовком, не проверив сценарий приложения.
- Ошибки посетителю — понятные и без секретов/путей. В логи не попадают тела авторизационных POST, токены или служебные URL; проверить конфигурацию хостинга, а не только свой код.
- PHP lint обязателен для изменённых PHP-файлов. Проверить GET/POST и выдачу assets в реальном окружении; unit-тесты добавлять для нетривиальной логики, если она появится.

## 7. Bitrix24 и асинхронные операции

- Инициализировать SDK до вызовов; использовать актуальные официальные контракты методов. Стадии, воронки, права и доступные поля загружать из портала, не придумывать.
- Не переносить случайный пример webhook или серверного OAuth в браузерное приложение. Авторизация остаётся штатной для выбранного SDK/типа установки.
- Сбор списка отделён от удаления. Учитывать пагинацию, повторные ID, изменяющуюся CRM и неготовый список.
- Единственный путь отправки DELETE проходит через проверку подтверждённого контекста и ID. В UI и адаптере не должно быть второго обходного пути.
- Различать сетевой отказ до отправки, потерю ответа после отправки, ошибку конкретной команды и успех. Не делать вывод «ничего не удалено» из таймаута.
- Ограничить конкурентность и повторы; параметры темпа держать в одном месте. Ошибки доступа и неверные параметры не повторять бесконечно.
- Локальный requestId помогает отслеживать операцию, но не обеспечивает серверную идемпотентность. Повторные отправки требуют сверки.
- Логи содержат минимум: идентификатор локальной операции, категорию ошибки и безопасные технические поля. Секреты и полные карточки не писать в диагностику.

## 8. IndexedDB

- Контекст хранения включает портал, пользователя, тип и операцию; схема версионируется. Не полагаться на localStorage как на единственное хранилище критического состояния.
- Изменения локального состояния объединять в короткие транзакции. Сетевой запрос выполнять вне открытой транзакции: сначала подтвердить сохранение намерения, затем отправить запрос, затем сохранить ответ новой транзакцией.
- Не считать отдельное событие успешного запроса доказательством фиксации всей транзакции; дождаться её завершения. [Использование IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB).
- Сохранять неизвестный исход при восстановлении отправленной, но неподтверждённой записи. Не определять его только по отсутствию карточки.
- Предусмотреть отказ записи, нехватку места, блокировку обновления другой вкладкой и миграцию старой схемы. При невозможности сохранить состояние новые удаления остановить.
- Срок хранения, очистка истории и поддержка браузеров должны соответствовать принятому продукту. Никаких обещаний восстановления после удаления данных браузера.

## 9. Тестирование и критерии готовности

Для отбора, подтверждения, переходов состояний, повторов и восстановления сначала задаём ожидаемое поведение и воспроизводящий тест, затем реализацию. Регрессия ошибки должна проверять исходный сбой. Для простой правки текста или CSS достаточна соразмерная проверка; не создавать тест, который лишь повторяет реализацию.

- Чистая логика: граничные значения, ревизии, исключения, лимит 3 000/3 001, переходы и согласованность счётчиков.
- Адаптер: корректные и некорректные ответы, отдельные ошибки пакета, временные отказы, таймауты. Имитация может ошибаться — важные контракты проверяем отдельно в Bitrix24.
- UI: действия пользователя и наблюдаемый результат, а не внутренние имена state. Запросы к элементам по роли/подписи. [Принципы Testing Library](https://testing-library.com/docs/guiding-principles/).
- Короткий набор сквозных сценариев: поиск → исключение → подтверждение → отчёт; обрыв → сверка → продолжение; отмена; другой портал.
- Таймеры и случайные задержки в локальных тестах контролируемые. Долгий sleep не заменяет ожидание конкретного состояния.
- Живые удаления — только в согласованной серии по точным искусственным ID; CI и обычный локальный тест не чистят настоящий портал.

На этапе каркаса настроить: ESLint с правилами React Hooks и проверки необработанных Promise, форматирование, TypeScript-проверку, тестовый раннер и сборку. Vitest, React Testing Library и Playwright — предлагаемый набор; совместимость подтверждаем при выборе версий. Не писать фиктивные команды в README до их успешного запуска.

Перед завершением задачи: соответствующие проверки пройдены, пользовательские изменения сохранены, STATUS актуален, нет скрытых ошибок и расширения архитектуры. Для релиза дополнительно закрываются применимые случаи TEST-MATRIX. Процент покрытия сам по себе не является критерием безопасности.
